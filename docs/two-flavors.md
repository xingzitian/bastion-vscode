# 两个版本的能力对照（VS Code 扩展 / 桌面版）

> 这份文档的存在理由：我们对外说过「**一个程序两个呈现**」，这句话只对**交互形态**成立 ——
> **实现是两份独立代码**（TypeScript 扩展 vs Go + React 桌面），能力**部分重叠、各有独有**，
> 而且**桌面版目前明显落后**。
>
> 写清楚是为了两件事：① 下载 exe 的人知道边界在哪；② 我们自己别再含糊地说"两个呈现"，
> 也避免"以为改了这边就等于改了两边"。

实测时间：2026-09-14。数字会变，结论（两套实现 + 桌面落后）在重构之前不会变。
最近一次更新：桌面版补上了「会话登记表 + 命令执行引擎 + MCP 出口」（5 个工具），
它**不再是完全没有 AI 能力**的那一版 —— 细节见第四节。

## 一、规模：这不是同一份代码

| | 桌面版 `bastion-shell` | VS Code 扩展 `bastion-vscode` |
|---|---|---|
| 语言 | Go **3,411 行**（手写，不含内嵌的 trzsz-go）+ React/TS **5,127 行**；另有 Go 测试 1,514 行 | TypeScript **12,803 行**（不含测试） |
| 宿主 | Wails 原生窗口（WebView2）+ `127.0.0.1:18090` 自带后端（HTTP/WS）+ `127.0.0.1:39311` MCP 端点 | VS Code 扩展宿主（Pseudoterminal） |
| 终端 UI | xterm.js（自己渲染） | VS Code 内置终端 |
| 分发 | exe（GitHub Release） | 扩展市场（自动更新） |

## 二、两边都有（各自实现）

- SSH 连接（含**连接复用**：一次认证多开会话）
- **rz/sz 文件传输**（ZMODEM；桌面版还把 lrzsz 二进制内嵌进去了，目标机没装也能用）
- 端口转发、广播输入、快捷命令、主题、多会话
- 密码存系统凭据库（桌面：Windows DPAPI；扩展：VS Code SecretStorage）
- 原生文件对话框、多目标批量连接

## 三、桌面版独有（扩展没有）

- **分屏 / 多标签**（`SplitPane.tsx`、`store/split.ts`、`store/tabs.ts`）
- **终端高亮规则**（`highlight.ts` 276 行 + `HighlightRulesDialog`）—— 按规则给输出上色
- OSC52 剪贴板、原生窗口（不依赖编辑器）

## 四、桌面版已经补齐的部分（**这一节是 2026-09-14 之后的新状态**）

| 能力 | 桌面版现状 |
|---|---|
| **会话登记表 + 输出滚动缓冲** | ✅ 有（`session.go`）。这是所有"从旁边看一眼/操作一下"能力的地基 |
| **命令执行引擎**（哨兵标记 + 退出码 + 输出静止兜底） | ✅ 有（`exec.go`），判定逻辑与扩展侧同一套 |
| **MCP 出口** | ✅ 有，**8 个工具**：`listSessions` / `health` / `tail` / `listProfiles` / `exec` / `habits` / `push` / `pull`（只差 `connect`） |
| **传输标准工具** | ✅ 有（`transfer.go`）：能力探测 → rz / base64 降级 / 目录 tar 打包 → 传完回读校验（哈希为准，不看 mtime） |
| **高危命令拦截** | ✅ 有（`danger.go`），规则与扩展侧同一份文件 |
| **个人习惯** | ✅ 有，且**参与行为**（记成免密 sudo 时 exec 才敢加哨兵） |
| **菜单识别** | ✅ 部分：只用于**拦**（不在菜单上发命令），不用于**自动走** |
| **官方 MCP SDK 互操作** | ✅ 已验证（同一份官方 SDK，22 项检查全过，含真文件传输） |
| **共享规则 JSON** | ✅ 三类规则（菜单/高危/习惯）**两个实现读同一份文件**（`~/.bastionshell/*.jsonc`） |

## 五、仍然只有 VS Code 扩展有（桌面版缺）

| 能力 | 桌面版现状 | 缺了会怎样 |
|---|---|---|
| **AI 自己连一台新机器**（`bastion_connect`） | 没有 | AI 只能操作**人已经手动登录好**的会话；连目标机、过菜单、选资产仍然是人的活 |
| **菜单"自动走"** | 没有（只有识别 + 拦截） | 数字列表菜单（`Opt>` 那种）、**一个 IP 匹配多条资产**、选用户分支，全部要人手动过 |
| **部署执行与报告** | `deploy.go` 只有 25 行（就挂了个"选文件"接口），执行靠前端薄编排 | 没有逐条命令的输出捕获、没有 Markdown 报告、失败定位全靠人看终端 |
| **rsync 增量同步** | 没有；`SyncDialog` 是空壳 | 大目录同步只能整包传 |
| **只读模式、AI 桥接（选中发给 AI）** | 没有 | — |

反向的那一半：**终端高亮规则、分屏/多标签、OSC52、原生窗口**是桌面版独有，扩展没有。

## 六、为什么会分裂，代价是什么

1. **同一个 bug 要修两遍**（甚至只修一遍就以为修好了）。
   *已经发生的例子*：base64 拉文件时兜底那条 `base64` 没吞 stderr，文件不存在时错误信息
   混进 payload，报出来是 `illegal base64 data at input byte 6`；哨兵用固定字符串 + `indexOf`
   时会被**命令回显**截走。这两处在扩展侧是潜在问题（回显被标记机制顺手去掉了），
   在桌面版实机测试里被逼出来后才两边一起修（2026-09-15）。
2. **规则类的东西最容易跑偏**：堡垒机菜单提示是可配置的**正则/数据**，而且实测过好几家厂商 ——
   *这条已经动手解决了*：菜单规则、高危规则、个人习惯现在放在**共享文件**
   （`~/.bastionshell/*.jsonc`），两个实现读同一份；内置默认仍各留一份代码常量（它们很稳定、不常改），
   但"新增/关掉一条规则"不用再改两处代码。
3. **能力只会单向堆积**：这一轮把"地基 + 传输 + 规则"补齐了，剩下的是 `connect`（菜单自动走）
   和部署报告 —— 都是"必须在 Go 里再写一遍"的部分。

> 关于上传权限 0000 那个 bug —— **已经实测清楚了（2026-09-15）**：
> - 扩展侧：已修复并在真机验证（本地与远端 md5/大小/mtime 一致，权限 `-rw-r--r--`）；
> - 桌面版：在装了 lrzsz 的靶机上**实测 rz 上传**，远端文件权限是 **644**（属主正确、`[ -r ]` 可读、md5 一致），
>   **没有 0000 问题**。根因是它用**内嵌的真 lrzsz（`sz.exe`）**当发送端，而当初那个 bug 在我们
>   **手写的 ZMODEM 发送器**里（自己拼 ZFILE 帧时把权限位写成了 0）。
> - 也就是说：之前"桌面版那份 rz 路径仍然是 0000"是**推断，而且推断错了**。现在两边都是实测结论。
> - 桌面版的传输工具在回读时会**实打实检查 `[ -r ]`**，权限不对会显眼地报出来 —— 这类"传上去等于白传"不会再悄悄溜过去。

## 七、怎么办（当前决定）

**短期（现在）**：桌面版保留"能用但不全"的定位，开发重心放在 VS Code 扩展 + MCP。
地基（登记表 / exec 引擎 / MCP 出口 / 标准传输 / 共享规则）已经补齐 ——
这几样无论后面走哪条路都不浪费。

**下一步（按性价比排序）**：
1. **`bastion_connect`（AI 自己连机器）**：依赖菜单"自动走"，是剩下这几项里最容易在真机上翻车的
   （用友/齐治/JumpServer 的菜单差异）。做之前建议先把菜单规则**在真机上多测几家**。
2. **部署执行与报告**：exec 引擎现成，缺的是逐条捕获 + Markdown 报告 + 上传走 `pushPath`。
3. **rz/sz 通道的实机验证**：给一台靶机装 lrzsz，把桌面版"上传权限到底是不是 0000"实测掉。

**长期（真正的解法）**：抽一个本地守护进程当"会话宿主"：

```
bastiond（持有会话 + 菜单识别 + exec 引擎 + MCP 出口）
   ├─ VS Code 扩展（瘦身成：终端视图 + 编辑器集成）
   ├─ 桌面窗口（现有 React UI 基本可复用，变成薄前端）
   └─ CLI（`bastion exec/sessions/push`，任何能跑命令的 AI 都能用）
```

到那时"要不要依赖 VS Code"这个问题才会消失；在此之前，**扩展仍然是功能最全的那个**。
